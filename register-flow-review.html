Register Flow Review

Commit 82b9888  “feat: BE register flow added” Reviewed 2026-08-19 11 findings, all confirmed

The skeleton is right; the commit shipped mid-work. The contract type, the @Public() route behind OriginCheckGuard, the cookie set on success, keeping the refresh token out of the body, and the bounded DTO validation all follow the house pattern. But the duplicate-email path — the whole reason EMAIL_TAKEN was added — is a commented-out empty try/catch, a console.log writes the Argon2 password hash to the logs on every signup, and register hand-copied login’s tail while dropping two of its invariants. Most findings collapse on their own once register is reshaped to mirror login exactly.

Findings, ranked by severity

01
Critical Security backend/src/auth/auth.service.ts:60

Password hash written to the logs on every registration

console.log("created user", createdUser) prints the full UserEntity — Argon2 passwordHash and email included — to stdout. Everything on stdout lands in .dev/logs/backend locally and in whatever aggregator production uses; logs are readable far more widely than the database, so every signup hands out an offline-crackable hash, bypassing the repo’s never-return-an-entity DTO discipline at the log layer.

Fix — delete the line. It is debug leftover, not something to convert into a Logger call.

02
Critical Correctness backend/src/auth/auth.service.ts:57

Duplicate email returns 500 INTERNAL; EMAIL_TAKEN is never thrown

The try/catch was left commented out, so the users.email unique violation escapes as a raw QueryFailedError and AllExceptionsFilter collapses it to 500 { code: 'INTERNAL' } plus a stack trace in the error log. The client branches on code and cannot show “email already in use” — the most common registration failure presents as a server outage, and the EMAIL_TAKEN code added to contracts in this same commit has no producer anywhere.

Fix — catch the Postgres unique-violation (driver code 23505) and throw the existing ApiException.conflict helper with EMAIL_TAKEN. Keep relying on the DB constraint rather than a findByEmail pre-check, so the path stays race-free under concurrent submits.

03
Critical Correctness backend/src/auth/dto/register-dto.ts:8

Register lowercases the email; login doesn’t — permanent lockout

RegisterDto normalizes with trim().toLowerCase() but LoginDto passes the email through untouched, and findByEmail is an exact match. Register as Foo@Bar.com and it is stored as foo@bar.com; log in later typing the identical address and the lookup misses, the dummy-hash verify runs, and the correct password gets 401 Invalid credentials — forever, unless the user guesses to type lowercase.

Fix — one shared normalization applied to both DTOs (a shared decorator), or normalize once in AuthService so register and login cannot drift.

04
High Correctness backend/src/auth/auth.controller.ts:88

Register skips the presented-cookie revocation that login performs

Login reads the browser’s refresh cookie and revokes the session behind it before overwriting the single browser-wide cookie slot — a 12-line comment in AuthService.login explains why. Register never calls readRefreshCookie, so registering account B in a browser signed in as user A leaves A’s session alive for its full 30-day life: a ghost device in GET /sessions whose “Revoke” does nothing observable, exactly the bug login just fixed.

Fix — pass the cookie into register and revoke before issuing, as login does. Better: extract one private revoke→create→issue tail both methods call, so the invariant lives in one place instead of a hand-copy.

05
High Correctness backend/src/auth/dto/register-dto.ts:8

Unguarded @Transform turns a malformed body into a 500

Transforms run before validation, and value.trim() has no string guard — so a body of {"email": 123} throws TypeError inside the ValidationPipe and surfaces as 500 INTERNAL on a public, unauthenticated route. LoginDto, with no transform, correctly returns the 400 VALIDATION envelope for the same input.

Fix — typeof value === 'string' ? value.trim().toLowerCase() : value, letting @IsEmail reject non-strings through the normal validation path.

06
High Correctness backend/src/auth/auth.controller.ts:98

A fall-through path answers 200 OK with an empty body

The service’s dead if (createdUser?.id) … else {} widens its return type to IssuedAuth | undefined, and the controller’s if (issued?.refreshToken) guard lets the handler fall off the end: HTTP 200, empty body, no cookie. The frontend treats any 2xx as signed-in and crashes reading accessToken/user off undefined — a failure dressed as success. One restored-and-swallowing try/catch away from being a live path.

Fix — declare register(): Promise<IssuedAuth>, delete the branches (usersService.create either returns an entity or throws), and make the controller tail unconditional like login’s. The compiler then enforces a total response.

07
Medium Test coverage backend/src/auth/auth.controller.ts:82

No tests shipped with the route

No unit spec, no e2e case, no extension to the existing auth specs. Every finding above would be caught by the e2e shapes the plan already prescribes: register → 201 + cookie + the token works on GET /tasks; duplicate register → 409 EMAIL_TAKEN; case-variant duplicate → 409; register from a logged-in agent → the old session’s token 401s. Mind the cleanup: these tests create users, so afterAll must delete them, not just sessions.

08
Low Simplification backend/src/users/users.service.ts:24

A single INSERT wrapped in an un-awaited transaction

One statement is already atomic, so the wrapper buys nothing and costs BEGIN/COMMIT round-trips plus a dedicated pooled connection per signup. The transaction(...) call is also never awaited inside the method — it only works because the async function’s implicit return awaits the promise; any post-processing added before the return would dereference a Promise.

Fix — return this.usersRepository.save(this.usersRepository.create({ email, passwordHash, name })). That single save is also the natural place to catch 23505 for finding 02.

09
Low Simplification backend/src/auth/auth.service.ts:56

Dead scaffolding shipped in the service

let createdUser = null immediately reassigned, an empty commented-out try/catch, and an empty else branch. Together they make null-handling look intentional where null is impossible — and make the duplicate-email path look handled when it is not, so the reader who should add the real catch assumes it exists.

Fix — flatten to straight-line const code. The only branch register needs is the real 23505 → EMAIL_TAKEN catch.

10
Low API design backend/src/auth/auth.controller.ts:82

200 where 201 belongs

Register creates a resource; @HttpCode(HttpStatus.OK) makes it indistinguishable from login’s deliberate 200 in monitoring and to API consumers — “new account created” and “existing credentials exchanged” read identically. One decorator change while the route is young and unconsumed.
